### 2026-06-18 — 0.2.0 (scope collapse: OFF integration disqualified, fixture-only path)

- Change: Created `025-tesco-product-enrichment/` as a Draft feature investigating alternative data sources for filling the product enrichment gap that the existing Tesco Apollo cache pipeline (spec 021) cannot close. The spec captures: (a) the data gap (Danny reports picture, description, storage, and preparation missing on a material fraction of receipt items), with a structured taxonomy of failure modes G1 (no tpnc resolved: search miss, Akamai block, substitution mismatch, delisted product), G2 (tpnc resolved but Apollo cache empty/malformed: Clubcard offer page, Marketplace listing, parser brace-counter miss, page redirect), G3 (Apollo extraction succeeded but fields empty: seasonal, new launches, sparse private label), and G4 (TTL expired and re-fetch failed); (b) a survey of eight candidate sources S1-S8 (Tesco Apollo, Tesco search-page HTML, Open Food Facts, Tesco Developer API, Edamam, USDA FoodData Central, aggregator services, curated static fallback) with per-source fields, data quality, ToS/legal, rate limit, auth, freshness, and reliability ratings; (c) a proposed layered fallback architecture (Apollo primary → Tesco search-page HTML → OFF per-field fallback for ingredients/allergens/nutrition → curated static → placeholder) with explicit exclusion of paid aggregators (S7), Edamam (S5), USDA (S6), and the Tesco Developer API (S4); (d) 14 functional requirements (FR-001..FR-014), 5 non-functional requirements (NFR-001..NFR-005), 4 user stories (US1 diagnose the gap, US2 extend curated static, US3 optional OFF enrichment, US4 no aggregator escalation), 10 acceptance scenarios (AS-001..AS-010), 6 open questions (gap size measurement, curated static priority, OFF coverage verification, OFF nutriments rendering, classifier input source, G1a vs G1b distinction), and a Promotion Criteria block that requires the diagnostic script (US1) to run before the spec can promote to Final; (e) a `tasks.md` that contains zero implementation tasks beyond the diagnostic script and the curated-static extension, both of which are gated on the diagnostic's output. The architecture is intentionally non-additive: it does NOT replace spec 021, it documents the design decision record for whether to add OFF, Edamam, or aggregators as fallback layers behind Apollo. The spec is Draft because the gap size is unmeasured and the implementation decision is unmade.
- Status after change: Draft
- Rationale: Danny asked on 2026-06-17 "can we fill in the missing picture / description / storage / preparation on items in the dashboard?". The natural answer is to survey the available sources, weigh the tradeoffs, and decide which to add (or whether to accept the gap). This Draft is the structured survey. The four user stories correspond to the four possible decisions Danny might make after reading the diagnostic: (US1) measure the gap; (US2) curate the obvious repeat-buys; (US3) add OFF as an ingredients/allergens/nutrition fallback (not storage/preparation); (US4) refuse to escalate to paid aggregators. The exclusion of paid APIs (FR-013) and the codification of the architecture diagram as the canonical reference (FR-012) are explicit so a future spec author cannot accidentally add Edamam or an aggregator without re-opening this one. The 6 open questions are deliberately unresolved in this Draft — they are the gate to promotion. The Promotion Criteria block is unusual: it does NOT require code to ship for promotion to Final, only that the design decision be made and recorded. This matches the convention Danny has confirmed on 2026-06-17 that specs are used "to think through problems" and that "the design and tradeoffs are the point, the implementation is downstream".
- Implementation impact: None (Draft). When promoted to Proposed or Final, expected changes per `plan.md` Step 2: either zero changes (Danny accepts the gap), one follow-up spec (026, 027, or 028 depending on which failure mode dominates), or two follow-up specs (curated static + OFF, or search fix + parser fix). The follow-up specs are NOT owned by 025; they get their own IDs. New files in this Draft: `025-tesco-product-enrichment/spec.md`, `plan.md`, `tasks.md`, `scenarios.yaml`, `traceability.yaml`, `CHANGELOG.md`, `references/tesco-product-enrichment-sources.md`. New files referenced by `plan.md` Step 3 (when Phase 4 runs, owned by separate spec): `lib/off-client.ts`, `lib/off-client.test.ts`.
