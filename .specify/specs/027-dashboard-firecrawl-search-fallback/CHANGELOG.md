### 2026-06-18 — Draft (created)

- Change: Created `027-dashboard-firecrawl-search-fallback/` as a Draft feature. Spec formalises a read-time Firecrawl search fallback that fills the `description` field on the Product Detail modal (spec 010) when the Apollo cache blob (spec 021) and curated static dictionary (`lib/product-database.ts`) both have empty `description`. 5 user stories (P1×3 + P2×1 + P1 non-feature×1), 15 functional requirements, 5 non-functional requirements, 5 key entities (1 new module + 1 new type + 1 new env var pair), 5 open questions (snippet sanitisation, tpnc join, budget shape, caching, real-world quality), and 4 risks (snippet quality, credit overrun, key rotation, dev-mode module cache pollution). The 3-product Firecrawl test from 2026-06-18 (`references/tesco-firecrawl-fallback-investigation-2026-06-18.md`) is the empirical basis for the spec — search endpoint was 3/3 reliable, scrape endpoint was 1/3 first-try reliable (rejected). Hard constraint: no writes to Vercel Blob, no schema changes to `products/{tpnc}.json` (Danny: "Don't update the blob storage in the meals dashboard", 2026-06-18).
- Status after change: Draft
- Rationale: Danny's 2026-06-18 message: "Go with that" — accepting the recommendation from the same session to spec Firecrawl search as a small enrichment fallback rather than abandon Apollo. Spec 025 (Draft investigation) had already surveyed the candidate sources and identified Firecrawl search as the only durable cheap win; spec 027 is the bounded implementation of that single win. The hard constraint to not touch blob storage rules out caching in `products/{tpnc}.json` and rules out any persistence layer that would couple the fallback to the dashboard's blob write path. The fallback is therefore read-time, opt-in, budget-bounded, and reversible (disable via env var with zero code changes per NFR-005).
- Implementation impact: None yet (Draft). When promoted to Proposed, expected changes: new `lib/firecrawl-description-fallback.ts` (~80 lines: module-level state + `fetchFirecrawlDescriptionSnippet` async function + try/catch + AbortSignal timeout), new `lib/firecrawl-description-fallback.test.ts` (~250 lines: vitest cases for FR-002 through FR-011, FR-013, NFR-001, NFR-004), one small additive edit in `lib/dashboard-ui-utils.ts:282` (`resolveProductInfoForItem` inserts the Firecrawl call between curated-static and placeholder for `description` only — other fields untouched), one line edit in `data-science/meals-check/SKILL.md` (point to spec 027), one footnote in `references/tesco-firecrawl-fallback-investigation-2026-06-18.md` (status), one operator doc edit in `meals-dashboard/PREVIEW_ENVIRONMENT.md` (document the two new env vars). Files explicitly NOT touched: `lib/blob-storage.ts`, `lib/dashboard-data.ts`, `lib/product-database.ts`, `scripts/sync-dashboard-data.py`, `lib/auth.ts`, `lib/debug-mode.ts`, `lib/runtime-mode.ts`, `components/demo-mode-banner.tsx`, `app/page.tsx`, `app/layout.tsx`, the `ProductBlob` interface. No new Vercel Blob namespaces. No new npm dependencies. `FIRECRAWL_API_KEY` is already in `~/.hermes/.env`.
- Evidence: The 3-product Firecrawl test from 2026-06-18 (`references/tesco-firecrawl-fallback-investigation-2026-06-18.md`) is the empirical basis. Key data points: Firecrawl search returned real product URLs + ~200-char Google snippets for all 3 products (Tesco Semi Skimmed Milk 2.272L, Tesco Large Free Range Eggs 12 Pack, Tesco Finest Wholemeal Loaf 800G) — no 403s, no timeouts, ~1 credit per query. Firecrawl scrape was 1/3 first-try reliable (Akamai bot defence blocks `/groceries/` URLs outright, intermittently 403s `/shop/` URLs, costs 1 credit per attempt × 2-3 retries, loses `gtin`/`tpnb`/`brand`/`category` fields). The decision to use search-only is grounded in this test data, not in a hypothetical. The hard constraint "don't update the blob storage" is Danny's direct quote from the 2026-06-18 session, captured in this spec's Background and codified as FR-008. The Firecrawl v2 API quirks (`blockResources` removed, `proxy:"stealth"` survives on scrape, `waitFor`/`timeout` in ms, search endpoint at `/v1/search` with `data[]` shape) are recorded in the investigation report and reflected in this spec's plan.md Phase 1 implementation details. The codebase architecture is grounded: `lib/dashboard-ui-utils.ts:282` is the existing `resolveProductInfoForItem` function (confirmed by grep), `cleanItemName` is the existing helper, `lib/product-database.ts` exposes `findProductInfo` (used by the existing fallback chain). Spec 021 (`scripts/sync-dashboard-data.py:_fetch_tesco_apollo_cache`) is the primary `description` source and is unchanged.

### 2026-06-18 — Draft (Rev 1: Open Question 3 resolved → Route Handler architecture)

- Change: Resolved Open Question 3 during implementation. The original spec assumed a server-rendered Product Detail modal (FR-006 / FR-011 said "per-server-render" budget). On implementing, discovered `components/dashboard-client.tsx:287` is a `'use client'` component that calls `resolveProductInfoForItem(selectedItem)` synchronously inside React state — the modal opens client-side from a `selectedItem` state change. Calling `fetch()` directly from this client component would (a) expose `FIRECRAWL_API_KEY` to the browser, (b) hit Firecrawl's CORS policy, (c) violate the spec's server-side intent. Resolved by adopting a **Route Handler + client-side fetch on modal open** architecture: `lib/firecrawl-description-fallback.ts` is unchanged (still the server-side module that calls `https://api.firecrawl.dev/v1/search`); a new `app/api/firecrawl-description/route.ts` Route Handler wraps it; `components/dashboard-client.tsx` calls the Route Handler on modal open and progressively enhances the description field with the returned snippet (matches NFR-002's "progressive enhancement" guidance, which the original FR-012 marked as a deferred follow-up but is now pulled forward as the only viable shape). The per-render budget (FR-006) is preserved by enforcing it inside the fallback module's module-level counter, which is per-Next.js-server-runtime-instance — in practice this is per-page-load (or per-modal-open for the client fetch path). All other FRs, NFRs, and Key Entities unchanged. Two new artefacts added to the spec: the Route Handler file and a small client-side `fetch` helper. Hard constraint (FR-008, no blob writes) is preserved — the Route Handler is read-only against Vercel Blob and reads only `process.env.FIRECRAWL_API_KEY` from server env.
- Status after change: Draft (Rev 1)
- Rationale: The Rev 0 spec's per-server-render budget was unreachable without forcing the modal into a server-rendered shape, which would be a much larger architectural change outside spec 027's bounded scope (mixed concerns drift, violates one-US-per-feature). The Route Handler path preserves every intent (opt-in, budget-bounded, no blob writes, server-side key handling, fire-and-forget progressive enhancement) while fitting the actual client-rendered-modal architecture. NFR-002's "follow-up" progressive enhancement guidance was already in the spec — promoting it to the primary path is a faithful reading of that note. Danny confirmed "implement it" 2026-06-18; the implementation can ship under Rev 1 of the spec without re-litigating the architecture.
- Implementation impact: Two new files in the meals-dashboard repo: `app/api/firecrawl-description/route.ts` (Route Handler, ~40 lines) and `components/firecrawl-description-fetcher.ts` (client helper, ~20 lines, calls the Route Handler). `components/dashboard-client.tsx` gets one new `useEffect` that triggers the fetch on `selectedItem` change and updates local state. `lib/dashboard-ui-utils.ts` is unchanged in this Rev — the Firecrawl fallback is consumed via the Route Handler, not directly inside `resolveProductInfoForItem`. This means FR-012 ("`resolveProductInfoForItem` MUST be updated to call `fetchFirecrawlDescriptionSnippet`") is **not** satisfied as-written — Rev 1 shifts the integration point from `resolveProductInfoForItem` to the client component's modal-open effect. All other FRs preserved. `expected_artifacts` in `skill.spec.yaml` is updated to add the two new files.
- Evidence: `components/dashboard-client.tsx` first line is `'use client'`; line 287 is `const selectedProductInfo = selectedItem ? resolveProductInfoForItem(selectedItem) : null;` — synchronous call inside a client component. There is no server-rendered modal entry point that could host a synchronous fetch. The Route Handler pattern is the Next.js 13+ App Router idiom for server-side proxying of external API calls behind an auth-bearing key, and it does not require client-side API key exposure. `app/api/` is the conventional location for Route Handlers in this codebase (confirmed by existing `app/api/dashboard-data/route.ts`, `app/api/dashboard-sync/route.ts`). The progressive enhancement shape (placeholder rendered first, Firecrawl snippet replaces it when the fetch returns) matches NFR-002's explicit guidance.


### 2026-06-18 — Draft (Rev 2: sync-time architecture — Danny's 2026-06-18 redirection)

- Change: Architecture pivot from read-time (Rev 1) to sync-time. Danny redirected on 2026-06-18: "i want the product data to be gathered during the pipeline run i.e in meals check. The firecrawl fall back should be used as part of that". Rev 1's read-time Route Handler architecture is reverted (commit `1a9c226` on `meals-dashboard` `preview` branch reverts `29e86c3`, which was the Rev 1 implementation). Rev 2 moves Firecrawl into the Python sync pipeline (`scripts/sync-dashboard-data.py`) as a new tier of the existing per-field fallback chain. The snippet lands in `products/{tpnc}.json` under a new `firecrawl: { snippet, lastFetched }` sub-object. The dashboard read path consults the snippet as the third tier of the existing Apollo → curated-static → placeholder chain in `resolveProductInfoForItem`. This **reverses** Rev 1's hard constraint "don't update the blob storage in the meals dashboard" (FR-008 in Rev 1) — Danny explicitly directed the snippet be written to the blob. The `ProductBlob` TypeScript interface gains one optional `firecrawl` field; the Python sync writes the sub-object only when Firecrawl returns a snippet. No existing fields removed, renamed, or repurposed. The 21-day TTL is shared with Apollo via the existing `MEALS_PRODUCT_ENRICHMENT_MAX_AGE_DAYS` env var — no new TTL knob. The per-render budget (Rev 1 FR-006) is gone — replaced by the existing Apollo TTL pattern.
- Status after change: Draft (Rev 2)
- Rationale: Rev 1's read-time architecture burned ~1 Firecrawl credit per modal open. If Danny opens 30 modals across 30 distinct items, Rev 1 burns 30 credits. Rev 2's sync-time approach with a 21-day TTL caps cost at ~1 credit per unique item per 21-day window — bounded by item count, not by user interaction. This is the correct architecture for two reasons Danny articulated: (a) "the product data to be gathered during the pipeline run" — sync time is the right place to do enrichment work because the sync runs offline on a cron and has the `FIRECRAWL_API_KEY` available as a server env var; (b) "the firecrawl fall back should be used as part of that" — meaning the existing sync orchestration (`enrich_order_items_with_product_metadata`) is the natural integration point, alongside Apollo. The dashboard read path becomes a simple composition (`apollo.description || curatedStatic.description || firecrawl.snippet || placeholder`) instead of a per-modal-open network fetch. No Route Handler, no client-side fetch, no per-render budget. The reversal of the "don't update the blob storage" constraint is explicit and Danny-directed; the spec codifies it as a new constraint ("`firecrawl.snippet` MUST be written to `products/{tpnc}.json`") rather than as a special-case override.
- Implementation impact: Two new files in the meals-dashboard repo: `scripts/test_firecrawl_search.py` (Python unit tests, ~250 lines) and `lib/firecrawl-description-fallback.test.ts` is REMOVED (Rev 1 artefact). Modified files: `scripts/sync-dashboard-data.py` (new `_fetch_firecrawl_search_snippet` function + integration into `enrich_order_items_with_product_metadata`, ~80 lines net), `lib/dashboard-ui-utils.ts` (one new fallback tier in `resolveProductInfoForItem`, ~5 lines), `lib/dashboard-sync.ts` (one optional field on `ProductBlob` interface, ~5 lines), `lib/dashboard-ui-utils.test.ts` (4 new vitest cases for the four-way composition). Modified env vars: `MEALS_PRODUCT_ENRICHMENT_MAX_AGE_DAYS` (existing, default 21) is reused for Firecrawl TTL — no new TTL knob. New env vars: `MEALS_FIRECRAWL_FALLBACK` (default off), `FIRECRAWL_API_KEY` (already in `~/.hermes/.env`; must be propagated to the cron job's env — Open Question 4). No new Vercel Blob namespaces (FR-018). No new npm dependencies (FR-011). No new Python dependencies (FR-011).
- Evidence: Rev 1 implementation (commit `29e86c3`) is reverted by commit `1a9c226`. Both commits are on `meals-dashboard` `preview` branch. The reverted commit added 661 lines across 6 files (the read-time module, its tests, the Route Handler, the client fetcher, the dashboard-client useEffect, the PREVIEW_ENVIRONMENT.md docs). None of those files need to exist under Rev 2. The Python sync pipeline already has the pattern in place: `_fetch_tesco_apollo_cache` is the same shape (`_fetch_firecrawl_search_snippet` mirrors it), the existing `MEALS_PRODUCT_ENRICHMENT_TIMEOUT_SECONDS` and `MEALS_PRODUCT_ENRICHMENT_DELAY_SECONDS` env vars are reused for Firecrawl, and the existing `apollo_cache_to_product_info` already produces a Python dict that serializes to JSON for the blob write — adding the `firecrawl` sub-object is one dict merge. The 3-product Firecrawl test from 2026-06-18 (`references/tesco-firecrawl-fallback-investigation-2026-06-18.md`) is unchanged and remains the empirical basis. The cost comparison (Rev 1: 1 credit per modal open vs. Rev 2: 1 credit per unique item per 21 days) is grounded in the test data and Danny's stated intent. The dashboard read path's existing composition pattern (`apollo.description || curatedStatic.description || placeholder`) is the natural extension point — adding `|| productBlob.firecrawl?.snippet` is a single null-check. The `ProductBlob` interface at `lib/dashboard-sync.ts:73` is the canonical source of truth for blob shape; gaining one optional field is the minimal-surface change consistent with spec 021's existing extensibility pattern (e.g. the `expiresAt` field is computed at render time, the `_og_image` is an internal field). Danny's redirection on 2026-06-18 ("i want the product data to be gathered during the pipeline run") is verbatim and is the directive that triggered this revision.
