# Feature Specification: Dashboard Meal Card Matcher Accuracy

Feature ID: `011-dashboard-meal-card-matcher-accuracy`

Feature Name: Dashboard Meal Card Matcher Accuracy

Target Skill: `data-science/meals-check`

Created: 2026-06-11

Status: Final

Change history: CHANGELOG.md

## Problem Statement

The matched and missing items shown on meal cards in the weekly grid and in the meal detail overlay are generated by `tesco_matcher.py` pipeline output. For some meal types — particularly roast dinners and meals with ambiguous component words — the matcher produces items that are semantically wrong: items are listed as matched when they do not meaningfully cover the meal, and items are listed as missing when they should match. The matcher distinguishes impossible false positives from flexible ingredient preparation: raw potatoes can cover `roast potatoes` because the household can roast them, while potato skins/chips remain false positives. Roast dinner coverage also requires named components such as broccoli, so relaxing potatoes does not overstate coverage.

This is a pipeline matching accuracy problem, not a dashboard UI problem. The dashboard renders whatever the pipeline produces. Fixing this requires changes to `tesco_matcher.py`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Correct Matched/Unmatched Items on Roast Pork Meal Card (Priority: P1)

As Danny, I want the matched and missing items on my meal cards to accurately reflect what the Tesco order actually covers, so I can trust the dashboard and make better decisions about what's needed.

**Why this priority**: A meal card showing wrong matched items is worse than no information — it creates false confidence. "Roast pork, roast potatoes and veg" currently shows as `covered` with 7 matched items, most of which are wrong.

**Independent Test**: Run `tesco_meal_check.py --days 30 --output both`, inspect the dashboard cache for "Roast pork, roast potatoes and veg", and verify the matcher produces correct matched/missing items per the acceptance scenarios below.

**Acceptance Scenarios**:

1. Given the meal "Roast pork, roast potatoes and veg", When the matcher evaluates `Tesco Crackling Pork Loin Joint 637G`, Then it matches — this is a valid pork roast item.

2. Given the meal "Roast pork, roast potatoes and veg", When the matcher evaluates `Tesco Large Vegetable Stir Fry 570g`, Then it matches — this covers the "veg" component.

3. Given the meal "Roast pork, roast potatoes and veg", When the matcher evaluates `Tesco Finest Beef Dripping Roast Potatoes 800G`, Then it is correctly excluded for the potato component (beef ≠ pork protein guard) or matched only for potato if a later partial-protein fix is implemented.

4. Given the meal "Roast pork, roast potatoes and veg", When the matcher evaluates `La Famiglia Rana Spicy Pork & 'Nduja Fettuccine 814g`, Then it does NOT match — this is a pasta dish with pork in a sauce, not a roast pork dish.

5. Given the meal "Roast pork, roast potatoes and veg", When the matcher evaluates `Tesco Egg Noodles 300G`, Then it does NOT match — noodles are not roast potatoes.

6. Given the meal "Roast pork, roast potatoes and veg", When the matcher evaluates `Bannisters Farm 4 Cheese & Bacon Potato Skins 260G`, Then it does NOT match — this is a snack side, not a roast potato component.

7. Given the meal "Roast pork, roast potatoes and veg", When the matcher evaluates Calbee potato chips (Hot & Spicy, Seaweed & Salt), Then neither matches — chips are not roast potatoes.

8. Given the meal "Roast pork, roast potatoes and veg", When the matcher runs to completion, Then the coverage status is `partial` (protein matched + one side matched = partial; not `covered` without a proper roast potato component) and `coverage_score` reflects the actual matched components.

9. Given a corrected matcher, When `tesco_meal_check.py --days 30 --output both` runs, Then the dashboard cache reflects the corrected matched/missing items and the Vercel dashboard deploys with correct data.

10. Given the meal "Roast beef, roast potatoes, roast carrots, broccoli", When the matcher evaluates `Tesco Maris Piper Potatoes 2Kg`, Then raw potatoes match the roast-potato component because they can be cooked into roast potatoes.

11. Given a home-cooked roast meal has its primary protein, raw potatoes, and the remaining named vegetables matched, When coverage status is calculated, Then the meal can be `covered` even if no Tesco item name literally says `roast potatoes`.

12. Given the meal requires roast potatoes, When the matcher evaluates snack/side products such as potato skins or Calbee potato chips, Then those remain excluded and must not satisfy the roast-potato component.


### User Story 2 - Generic Expected Components for Partial Non-Roast Meals (Priority: P1)

As Danny, I want partial non-roast meals to expose targeted expected components, so the Meal Detail Overlay can show an `Expected Items` section for ordinary component meals, not only roast dinners.

**Why this priority**: The dashboard currently shows `Salmon (frozen) and potato slices and frozen veg` as `partial` but has no Expected Items section because the matcher only emits `missing_components` for roast-specific required components. That leaves the partial status unexplained.

**Independent Test**: Run the matcher against `Salmon (frozen) and potato slices and frozen veg` with only a potato grocery matched, then verify the result remains `partial` and emits targeted missing components such as `salmon` and `frozen veg` (or equivalent meal-specific component labels) for dashboard `Expected Items`.

**Acceptance Scenarios**:

13. Given `Salmon (frozen) and potato slices and frozen veg` is matched only by a potato item such as `Tesco Maris Piper Potatoes 2Kg`, When the matcher generates meal coverage, Then `status` is `partial` and `missing_components` is not empty.
14. Given the same meal has no matched salmon/fish item and no matched frozen vegetable item, When missing components are generated, Then the targeted expected components include the missing protein (`salmon`) and the missing vegetable component (`frozen veg` or equivalent), rather than a broad unmatched-grocery dump.
15. Given the dashboard consumes this matcher output, When the partial meal detail opens, Then spec 007 can render `Expected Items` from `missing_explanations` for this non-roast partial meal.

### Edge Cases

- The fix must not regress correct matches in other meal types — run full test suite after changes.
- "Pork" as a word in a ready-made product name (e.g. "Spicy Pork & 'Nduja Fettuccine") should not count as a protein match for a roast pork dish unless the product is actually a roast pork dish.
- Side dishes (potato skins, chips, egg noodles) should not match meal components via substring alone — they must meaningfully cover the component.
- Preparation adjectives in meal descriptions should be interpreted flexibly when the grocery is a raw ingredient that can reasonably be cooked that way; `roast potatoes` can be covered by suitable raw potatoes.
- Fuzzy matching should not push weak partial word matches over the threshold without protein or primary component support.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The matcher MUST NOT match a ready-made dish as a protein hit when the product is a different dish type (e.g. pasta with pork in the name is not a roast pork dish).
- **FR-002**: The matcher MUST NOT match side dishes (noodles, potato skins, chips) as meal components via substring or fuzzy hits alone.
- **FR-003**: The `meal_is_pork_dish` override MUST only fire when the substantive hit is the primary protein component of the meal, not when it's a side dish or unrelated ready-made dish.
- **FR-004**: Fuzzy match threshold MUST be gated — items that only get hits on generic meal words without protein or primary component support must not cross the threshold.
- **FR-005**: For "Roast pork, roast potatoes and veg", the matcher output MUST produce `partial` status (protein + one side), not `covered`, when no suitable potato component is present.
- **FR-006**: For home-cooked roast meals, suitable raw potatoes MUST satisfy the roast-potato component for coverage-status purposes.
- **FR-007**: The roast-potato flexibility MUST preserve existing false-positive exclusions: potato skins, potato chips/crisps, unrelated noodles, and wrong-dish ready meals MUST NOT satisfy roast potatoes.
- **FR-008**: The matcher SHOULD treat preparation words such as `roast` as modifiers rather than mandatory product-name tokens when a matched grocery is a plausible raw ingredient for that prepared component.
- **FR-009**: Roast dinner coverage MUST exclude wrong-format protein products such as burgers when the meal calls for roast beef/pork/lamb/chicken/duck.
- **FR-010**: Roast dinner coverage MUST require named non-protein components in the meal description, so a meal naming broccoli remains `partial` when broccoli is not matched.
- **FR-011**: For partial non-roast component meals, the matcher SHOULD emit targeted `missing_components` for unmatched meal-specific required components so dashboard `Expected Items` can explain the partial state.
- **FR-012**: For `Salmon (frozen) and potato slices and frozen veg`, when only a potato item is matched, targeted `missing_components` MUST identify the missing salmon/fish protein and frozen-vegetable component rather than remaining empty.

### Key Entities

- **Meal Card**: Weekly grid card showing meal name, status (covered/partial/missing), and matched/missing grocery items.

## Clarifications

### Session 2026-06-14 — Missing Expected Items for salmon/potato/frozen veg

- Q: Why did `Salmon (frozen) and potato slices and frozen veg` not show Expected Items? → A: The dashboard cache had `status = partial` and `missing_explanations = []`. The pipeline maps `missing_explanations` from matcher `missing_components`, and the current matcher only populates `missing_components` via roast-specific logic. Generic non-roast partial meals therefore have no Expected Items metadata even when obvious components such as salmon and frozen veg are missing.
