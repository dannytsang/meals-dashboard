### 2026-06-20 — Proposed (fixture-import fallback hardening)

- Change: Hardened the preview reader-selection path so the dashboard now uses a small `selectDashboardDataReader()` helper that keeps the priority order `blob > fixture > empty` but also catches a malformed bundled fixture import and falls back to `EmptyDashboardReader` instead of letting the page fail at module-load time.
- Status after change: Proposed
- Rationale: The spec's preview-mode contract is not just about missing fixture files; a malformed generated fixture should still degrade to the empty dashboard instead of crashing the page. This keeps the preview surface available while preserving the existing empty-state behavior for unreadable fixture artefacts.
- Implementation impact: Added `lib/fixtures/select-dashboard-data-reader.ts`, switched `app/page.tsx` to await the helper, and added a regression test that forces the bundled fixture import to fail and asserts the empty reader behaviour. `components/dashboard-client.test.ts` now source-checks the new helper wiring.
- Evidence: `npx vitest run lib/fixtures/select-dashboard-data-reader.test.ts components/dashboard-client.test.ts --reporter=dot` passed; `npx tsc --noEmit` passed; `npx next build` passed.

### 2026-06-17 — Draft (preview data segregation without provisioning a second blob store)

- Change: Created `024-dashboard-static-fixture-mode-for-preview/` as a Draft feature. Spec formalises a server-side runtime mode (`MEALS_FIXTURE_MODE`) that swaps the dashboard's blob-storage read path for a static, bundled JSON fixture when Vercel Blob is not configured. Spec captures: 20 functional requirements (runtime-mode helper, fixture reader, empty-state reader, badge component, dashboard wiring, no production regression, no fixture data leak into prod bundle), 7 non-functional requirements (latency, bundle size, privacy boundary, accessibility, prod-misconfig warning, no new deps, no network calls), 5 user stories (preview renders without blob, production unchanged, server-side only, graceful empty state, obviously-fake data), 7 resolved open questions (bundled in repo, single fixture, env-var opt-in, fixture priority over blob, hand-curated synthetic data, separate empty-state reader, separate runtime-mode module from spec 022), and 4 future considerations explicitly out of scope.
- Status after change: Draft
- Rationale: Danny asked on 2026-06-17 "is there a way to have static example data for preview so i don't have to setup another blob storage?" after disconnecting the blob storage from the preview Vercel environment. The codebase is already prepared for this feature: `lib/dashboard-data.ts:54` exports a `DashboardDataReader` interface; `getDashboardData({ coverageWindow, reader })` accepts an injected reader; tests already inject readers via `InMemoryBlobStorageClient`; the single injection point is `app/page.tsx:27`. The architecture work to enable this spec is essentially zero — only the new reader implementation, the runtime-mode helper, the bundled fixture, and the badge component are needed. This makes the feature low-risk and high-value: preview gets a usable dashboard, production is untouched, and the runtime mode is opt-in via env var.
- Implementation impact: None yet (Draft). When promoted to Proposed, expected changes: new `lib/runtime-mode.ts` (env-var helper), new `lib/fixtures/static-fixture-reader.ts` (implements `DashboardDataReader` against bundled JSON), new `lib/fixtures/empty-dashboard-reader.ts` (returns null/empty for misconfigured envs), new `lib/fixtures/dashboard-fixture.json` (hand-curated synthetic data), new `components/fixture-mode-badge.tsx` (server-rendered amber badge), small updates to `app/page.tsx` and `components/dashboard-client.tsx` (select reader at request time, render badge), tests for all new modules, and `PREVIEW_ENVIRONMENT.md` update for the operator-facing knob. The production read path is untouched. Estimated surface: ~250 lines of new code + ~200 lines of tests + 1 hand-curated JSON file ≤ 8 KB.
- Evidence: Existing architecture (spec 016 + 017) explicitly defines the `DashboardDataReader` seam and the reader injection point — `lib/dashboard-data.ts:54` defines the type as `Pick<BlobStorageClient, 'readPointer' | 'readManifest' | 'readJsonBlob' | 'listPaths'>`; `getDashboardData({ coverageWindow, reader })` defaults to `new VercelBlobStorageClient()` but accepts an override; `lib/dashboard-data.test.ts:1-2` and `:155` show tests already using the seam via `reader: readerOf(client)`. Adding two more reader implementations (`StaticFixtureReader`, `EmptyDashboardReader`) is the natural extension. The `VercelBlobStorageClient` constructor at `lib/blob-storage.ts:58` already reads `BLOB_READ_WRITE_TOKEN` from env; `isBlobStorageConfigured()` is a trivial wrapper around the same check. The fixture conforms to the `SplitLayoutPayload` shape that `lib/dashboard-sync.test.ts` already round-trips through `syncDashboardLayout(payload, client)`. Spec 022 (debug mode) precedent: `lib/debug-mode.ts` + `MEALS_DEBUG_MODE` env var is the exact pattern spec 024 follows for runtime-mode + `MEALS_FIXTURE_MODE` env var. The two specs are explicitly independent (different env vars, different files, different concerns) and coexist.

> **Note**: The 2026-06-17 "Draft" entry above describes the original Rev 0 design. The Rev 3 entry above supersedes the design decisions captured in this Draft entry: env-var opt-in is replaced by auto-detect; the dismissible badge is replaced by a permanent banner; the hand-curated "Sample" fixture is replaced by a build-time-generated trip-derived fixture. The architectural rationale (the `DashboardDataReader` seam, the production read path being untouched) is unchanged.
