# Implementation Plan: Dashboard Order History Retention

Status: Final
Feature: 035-dashboard-order-history-retention
Skill: data-science/meals-check

## Summary

Extend `scripts/sync-dashboard-data.py` to retain the most recent N (default 6) Tesco order receipts in a small gitignored on-disk sidecar (`data/orders/previously_synced.json`) and pack them all — plus the active receipt — into the dashboard payload's `orders[]` array. The dashboard loader already iterates whatever `OrderBlob` paths the payload exposes (spec 017), so no JavaScript / TypeScript changes are required for the fix to take effect: the spec 034 matcher will classify the retained historical orders as `previous` automatically because their `deliveryDate < today`.

## Technical Context

- **`scripts/sync-dashboard-data.py`** — the dashboard publish pipeline. CHANGED: introduces the sidecar read/write helpers (`load_historical_orders`, `persist_historical_orders`), an `assemble_orders(active, historical, cap)` pure helper, and wires both into `build_dashboard_payload` and the post-publish sidecar update step. CLI flag `--max-history` and `--no-history` added; the existing `--config`, `--verify`, and `--dry-run` flags remain unchanged.
- **`scripts/tests/test_sync_dashboard_history.py`** (new) — pytest unit tests for the merge logic, the sidecar CRUD, the cap/FIFO eviction, the CLI override paths, and the corrupt-sidecar recovery.
- **`scripts/data/orders/.gitignore`** (new line under `data/orders/`) — adds the sidecar plus future per-order archive to the ignore pattern. Currently the `data/` root is partially gitignored; we ensure the `orders/` subpath covers everything.
- **`meals-dashboard`** — UNCHANGED. The loader (`lib/dashboard-data.ts:202`) already passes through however many orders the payload exposes; spec 017 calls for `Promise.all(orderPaths.map(...))` which is N-agnostic.
- **`meals-dashboard`** test fixtures — UNCHANGED for this spec (no JS code change). If the chef wants to add a fixture-based assertion that the dashboard renders with `validOrders.length > 1`, that is a follow-up spec.
- **Vercel Blob** — UNCHANGED. Blob continues to retain everything; we only change what the publisher packs.
- **Crons / schedulers** — UNCHANGED. The new `--max-history` / `--no-history` flags are no-op-by-default; existing cron entries keep working.

## Implementation Phases

### Phase 1 — Pure helper + sidecar CRUD (TDD red → green)

- Add a `load_historical_orders(cap: int) -> list[dict]` helper to `sync-dashboard-data.py`. Reads `data/orders/previously_synced.json`; returns `[]` on missing file / JSON parse error / any I/O failure. Logs at INFO with a `safe-fallback` marker.
- Add a `persist_historical_orders(orders: list[dict])` helper. Writes the (already-capped) merged list back to the sidecar via `pathlib.Path.write_text(json.dumps(..., indent=2, sort_keys=True))`. Atomic via a `.tmp + os.replace` pattern so a crash mid-write does not corrupt the sidecar.
- Add a `assemble_orders(active: dict, historical: list[dict], cap: int) -> list[dict]` pure helper:
  1. De-duplicate by `orderId`, most-recent-wins (active overrides historical).
  2. Sort by `deliveryDate` ascending.
  3. Truncate to `cap + 1` entries (the +1 covers the active receipt even if it has the smallest `deliveryDate`).
  4. Return the resulting `list[dict]`.
- Add `MAX_HISTORICAL_ORDERS: int = 6` module-level constant.
- Add two argparse flags to the existing `main()`: `--max-history N` (positive int, capped at 50) and `--no-history` (boolean, default False).
- Add an INFO-level summary log line per FR-009.

### Phase 2 — `build_dashboard_payload` integration

- Read the sidecar at the top of `build_dashboard_payload(...)` (or factor that out into a wrapping helper, but stay close to the current structure for diff size).
- Call `assemble_orders(active_receipt, historical, cap)` and assign the result to the published `orders: []` field (replacing the current single-element or empty behaviour).
- After successful `publish_payload(...)`, call `persist_historical_orders(merged)` so the sidecar reflects what was just published (helps with `--dry-run` parity).
- When `--no-history` is set, the entire sidecar read/write is skipped and `orders[]` contains only the active receipt (legacy behaviour preserved).

## Risks

- **Blob size growth**: Even at cap=6, the payload stays well under 1MB. Mitigation: NFR-003 confirms budget headroom. Future-proofing: cap can be tuned later via spec update.
- **Sidecar corruption on crash**: The `.tmp + os.replace` pattern makes the sidecar atomic. Mitigation: FR-007 + the corrupt-sidecar test case.
- **Cron concurrency**: Vercel crons are serialised in practice; if a race ever happens, last-write-wins is acceptable because the merge logic is orderId-deduplicated.
- **Existing matcher tests**: Spec 035 does NOT touch the matcher; matcher tests are unchanged. The 21/21 + 1 pre-existing failure on the scripts repo remains pre-existing.
