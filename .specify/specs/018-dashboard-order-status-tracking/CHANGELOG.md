This feature owns order status tracking: cancellation detection, moved-order detection, refund detection, and the `status` field on order blobs. ### 2026-06-14 — Add cancellation and moved order detection (carried over from parent)

- Change: Original 016 spec added User Story 5 (Cancellation and Moved Order Detection) and three new functional requirements. Order blobs gained a `status` field: `"active"`, `"cancelled"`, or `"superseded"`. Pipeline must detect cancellation emails and moved orders. Cancelled and superseded order blobs are excluded from meal coverage. The `tesco_meal_check.py` email selection logic must include `cancelled` emails as valid candidates. Carried over verbatim and forms the basis of this feature.
- Status after change: Proposed (this slice)
- Rationale: Scenario 3.2 analysis revealed the current pipeline silently ignores cancellation emails and has no concept of order identity across delivery date changes. Without status tracking, a cancelled order's blob would remain in storage with no indication it was void.
- Implementation impact: `tesco_gmail.py`: add cancellation subject pattern. `tesco_meal_check.py`: include `cancelled` emails in valid candidates; add moved-order detection.
- Evidence: Code inspection of `tesco_gmail.py` line 100–112 (no cancellation case), `tesco_meal_check.py` lines 562–572 (valid email filter excludes cancelled emails), `tesco_meal_check.py` line 326–327 (order_number sourced from email, no cross-email deduplication).

### 2026-06-14 — Add refund handling — order status portion (carried over from parent)

- Change: Original 016 spec added FR-04 for refund handling. Refund emails are valid candidates; when received, the order blob `status` is set to `"refunded"` and the item list is updated to remove refunded items. Coverage invalidation triggered by refund is owned by `019`. Carried over verbatim and forms the basis of this feature's FR-04 and FR-07.
- Status after change: Proposed (this slice)
- Rationale: A refund email has real consequences — items are no longer available for meal coverage. The order blob must reflect this accurately.
- Implementation impact: `tesco_meal_check.py`: include `refund` in valid email candidates. On refund email: update order blob `status` to `"refunded"`, remove refunded items from item list, record refund amount.
- Evidence: Scenario 3.7 — refund email arrives after receipt; pipeline ignores it; coverage stays wrong.
