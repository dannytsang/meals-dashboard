### 2026-06-19 — Rev 2 (Debug menu row flipped from conditional to always-visible)

- Change: **FR-005** rewritten: the Debug menu row is now rendered **unconditionally** in the menu (regardless of the server-rendered `debugOn` prop) and reflects the current `meals_debug_mode` signed-cookie state via `aria-checked` (`'true'` when the cookie verifies to `'1'`, `'false'` otherwise). Clicking the row POSTs to `/api/debug/toggle` with the flipped value (`{ value: '1' }` when off, `{ value: '0' }` when on). **FR-013** clarified to spell out the flipped value explicitly. **US-2** rewritten with three new acceptance scenarios (AS-007: always-visible in off state when cookie unset; AS-008: click enables from off state by POSTing `{ value: '1' }`; AS-009: click disables from on state by POSTing `{ value: '0' }`). **AS-015** (US-4 Tab order) updated to "Debug" (no longer "Debug when present"). **Background** section: "conditional" wording flipped to "always-visible". **Promotion Criteria for Final**: the `Debug menu row is absent when the cookie is unset` requirement flipped to `Debug menu row is always-visible regardless of cookie state`. **Open Questions** added item 6 (Rev 2 resolution of the conditional-vs-always-visible question). **Key Entities**: `DebugMenuRow` description flipped from "Conditionally-rendered" to "Always-rendered ... per FR-005 Rev 2". **Verification Plan**: unit test description updated; end-to-end and regression manual checks flipped to assert the Debug row is present in both cookie states (the clean-slate session now sees the row in off state and can click to enable for the first time). **Spec Rev 2 callout banner** added above `Status:` line.
- Status after change: Proposed (no change to lifecycle — the Rev 1 implementation hasn't been promoted to production, so this is a pre-Final design correction)
- Rationale: On 2026-06-19, after the Rev 1 implementation was on the meals-dashboard `preview` branch (commit `dc9df90`), Danny reported "the debug menu option has disappeared". Investigation: the pre-spec-026 inline `<DebugToggle initialEnabled={!!debugOn} />` was rendered unconditionally and showed the current cookie state; Rev 1's spec 026 FR-005 made the menu's Debug row strictly conditional on `debugOn` being truthy (matching spec 022 line 45 wording), which closed the first-time-enablement path — users whose `meals_debug_mode` cookie was unset had no UI affordance to enable debug mode for the first time. This is the spec-design equivalent of breaking a one-way function: any spec that migrates an inline always-visible control into a conditional menu row silently removes the UI affordance for users who haven't yet reached the gated state. Danny's correction on 2026-06-19 — "i'm expecting it to be in the menu" — is unambiguous: the Debug row must always be visible. The fix is the canonical Rev 2 path from spec 027 Rev 2 (2026-06-18): write the spec amendment first (this entry), revert the prior implementation, then commit the new implementation on `preview`. Server-side cookie verification (spec 022 Rev 3) is preserved — the row's initial `aria-checked` reflects what the server has authorised; clicking the row POSTs and the server re-verifies on the next request.
- Implementation impact: Spec amendments land on `Hermes-Skills main` (this commit). Implementation revert + reimplement lands on `meals-dashboard preview` (separate commit). Source files to amend: `components/user-menu.tsx` (drop the `{debugOn && ...}` guard around the Debug row JSX; refactor `handleDebugClick` to POST `{ value: '1' }` when `debugEnabled` is initially false, `{ value: '0' }` when initially true — the existing `!next` computation already handles this case correctly, so the change is purely the JSX guard removal). Source files to amend tests: `components/user-menu.test.tsx` — replace the existing `does NOT render the Debug row when debugOn=false` test (lines 130-134) with a new test `renders the Debug row when debugOn=false with aria-checked="false" and clicks POST { value: '1' } to enable`. Update task T009 in `tasks.md` to mark it open again (Rev 1 marked it `[x]`). Update plan.md Phase 2 / T009 description. Promotion to `Final` is still gated on production deployment evidence per the Promotion Criteria for Final block.
- Evidence: Spec diff: `git diff ce5c44d -- data-science/meals-check/.specify/specs/026-dashboard-user-menu/spec.md` (will show FR-005, FR-013, US-2, Background, Promotion Criteria, Open Questions, Key Entities, Verification Plan updates). Validator output (post-amendment): pending — to be captured in the commit that lands this amendment. Implementation diff: pending — to be captured in the meals-dashboard `preview` revert+reimplement commit. The Rev 2 reference design is the `meals-dashboard-spec-authoring` skill's `references/conditional-affordance-ux-regression.md` (written 2026-06-19 specifically for this class of regression, with the three-questions checklist, the diagnostic recipe, and the worked example of what spec 026 Rev 2 should have said).

### 2026-06-19 — Implementation landed (meals-dashboard `preview` branch)

- Change: Implementation per plan.md Phases 1-3 on the `preview` branch of the meals-dashboard repo. Six files modified, four files added. Tasks T001-T019 marked complete in `tasks.md`. The two open items (T020 manual verification, T021 production deployment evidence) are the gates for Proposed → Final.
- Status after change: Proposed (no change)
- Rationale: Danny directed implementation on 2026-06-19. The spec was already at Proposed (commit `ce5c44d`) with a detailed plan, so the implementation followed plan.md directly without reshaping any FR. Two minor implementation notes that don't reshape the spec:
  1. **FR-006 localStorage key**: spec said `'meals-theme'`, the actual key in `lib/theme.tsx` is `'meals-dashboard-theme'`. The pure `toggleTheme()` helper in `lib/user-menu.ts` uses the actual key so its write is read by the existing `<ThemeProvider />` on the next mount. Pinning the key in a unit test (`lib/user-menu.test.ts`) prevents accidental divergence.
  2. **JSDoc comment in `dashboard-client.tsx`**: the comment that replaced the old `<UserChip />` / `<DebugToggle />` / `<ThemeToggle />` / `<SignOutButton />` references initially used the literal JSX-like syntax (`<UserChip />`) inside a `{/* ... */}` block. TypeScript's JSX parser treats these as JSX even inside JS comments and raises `Cannot find name 'X' [2304]`. Reworded the comment to drop the angle brackets.
- Implementation impact: New source files: `lib/user-menu.ts` (pure helpers, 12 unit tests passing), `lib/user-menu.test.ts`, `components/user-menu.tsx` (thin client component, 14 unit tests passing), `components/user-menu.test.tsx`. Modified files: `components/dashboard-client.tsx` (header action row restructured per FR-022), `components/dashboard-client.test.ts` (assertions updated per FR-022), `components/debug-toggle.tsx` (refactored to call `toggleDebug()` helper per FR-016), `components/theme-toggle.tsx` (unchanged — provider now calls the helper internally), `components/sign-out-button.tsx` (refactored to call `signOut()` helper per FR-016), `components/sign-out-button.test.ts` (assertions updated for the helper indirection), `lib/theme.tsx` (provider's `toggleTheme` now delegates to the pure helper per FR-016). No new npm dependencies. No changes to OIDC config, NextAuth, middleware, blob layout, sync script, debug-cookie signing, or any other dashboard feature not listed in this spec's Contract Impact section.
