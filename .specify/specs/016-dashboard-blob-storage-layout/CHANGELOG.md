### 2026-06-14 — Add content-hash dedup with blob-stored manifest (carried over from parent)

- Change: Original 016 spec replaced the simple mutable pointer+summary approach with a content-addressable hash manifest stored in Blob alongside the data. Every data blob is hashed with SHA-256 before writing; the manifest maps blob paths to hashes and is itself content-addressable by its own hash. Unchanged blobs are skipped entirely on subsequent syncs. Only the manifest (~1KB) and pointer (~50 bytes) are written on unchanged syncs — down from ~13.8KB across 9 blobs without dedup. Carried over verbatim from parent changelog and rewritten as the foundation of this feature.
- Status after change: Proposed (this slice)
- Rationale: A local dedup cache creates a single point of failure if Hermes state is lost. A blob-stored manifest is self-healing and portable. Content-addressable manifest paths (hash-of-content = blob path) eliminate circular write dependencies.
- Implementation impact: Full rewrite of sync blob write logic. New algorithm: (1) read pointer, (2) fetch current manifest, (3) compute local hashes, (4) write only changed blobs, (5) build new manifest including all paths, (6) write manifest to `meta/manifest-{hash}.json`, (7) write pointer to `pointers/latest.json`.
- Evidence: Python analysis of unchanged-sync scenario showed 9 blob ops / 13.8KB without dedup vs 2 blob ops / ~1KB with dedup.

### 2026-06-14 — Remove blob storage versioning; audit trail in meals skill (carried over from parent)

- Change: Original 016 spec removed blob-storage versioned blobs. Coverage blobs are overwritten in-place when content changes. Version history and audit trail moved to the meals skill's local `~/.hermes/scripts/data/audit.jsonl` file. Each blob write event is appended as a JSON line to this local file. Carried over verbatim and forms the basis of FR-12 in this feature.
- Status after change: Proposed (this slice)
- Rationale: Keeping every versioned blob in Blob storage would accumulate unbounded storage waste. A meal completed in Todoist 365 times a year would create 365 coverage blob versions per year in Vercel Blob. The meals skill's local audit log is the right place for version history; blob storage holds only current state.
- Implementation impact: Coverage blobs are overwritten in-place. `tesco_meal_check.py` appends a JSON line to `audit.jsonl` per blob write event. Manifest structure unchanged. Dashboard read path unchanged.
- Evidence: Scenario 3.3 analysis showed a meal completed daily would create 365 coverage blob versions per year in blob storage.
