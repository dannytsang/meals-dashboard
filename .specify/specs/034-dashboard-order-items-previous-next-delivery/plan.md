# Implementation Plan: Dashboard Order Items — Previous / Next Delivery

Status: Draft
Feature: 034-dashboard-order-items-previous-next-delivery
Skill: data-science/meals-check

## Summary

Adds a Previous / Next delivery classification to every item in the Order Items by Category section of the meals dashboard, derived purely at render time from `deliveryDate` vs `today` with zero pipeline or sync changes. The dashboard already loads every order blob in the visible manifest window (one loader call), so the classification runs as a pure O(n) derivation over the already-fetched `validOrders` plus a cross-reference with `deliveryWindows` for the pending-next case. A new section-level filter (`All / Previous / Next`) defaults to Next, persists across page reloads via sessionStorage, and composes with the existing search / category / match / sort pipeline as the first stage.

## Implementation Phases

### Phase 1 — Pure derivation helper (testable in isolation)

- Add `classifyOrderItemsByDelivery(items, orders, deliveryWindows, today)` to `lib/item-utils.ts`. Pure function; no React state, no side effects. Returns:
  ```ts
  type DeliveryGroup = {
    order: OrderBlob | null;  // null for pending-next entries (window without blob)
    deliveryDate: string;
    deliverySlot: string;
    status?: OrderBlob['status'];
    items: GroceryItem[];
    classification: 'previous' | 'next' | 'pending-next';
  };
  type ClassifiedOrders = {
    previous: DeliveryGroup[];
    next: DeliveryGroup[];
    pendingNext: DeliveryGroup[];
  };
  ```
  Sort each bucket by `deliveryDate` ascending (chronological; earliest first).
- Edge cases: malformed `deliveryDate` → excluded; duplicate `deliveryDate` across multiple `OrderBlob`s → merged into one `DeliveryGroup`; cancelled / superseded / refunded orders kept under whichever classification applies with their `status` field exposed.

## Why this approach over alternatives

- **Why not a cron-driven sync that rewrites order blobs with a `classification` field?** Because the dashboard already loads every order blob, and `today` is already known at render time. A sync would add a pipeline write that is stale by definition (cron runs at intervals; the dashboard renders continuously). The render-time derivation is always current at the moment of render.
- **Why not a `useEffect` that polls `today` and triggers a state change?** Because the dashboard already re-renders on every server-side data fetch (Next.js server component model). A timer would race with the existing render cycle and add complexity for no benefit.
- **Why not a URL query param for the filter?** Because spec 024 already uses URL params for fixture-mode toggles, and adding another URL param for a session-only UI state would conflict with the existing fixture-mode param scheme. sessionStorage is the right scope: session-only, no URL pollution, no multi-day staleness.
- **Why expose `validOrders` instead of deriving on the server and shipping only the classified groups?** Because the section's existing pipeline (search / category / match / sort) operates per-item and needs the raw item list, not pre-classified groups. Shipping the raw `validOrders` plus a `today` value is simpler and lets the client compose all the filters cleanly.
