## Entries

### 2026-06-30 — Draft (initial authoring)

- Change: Initial Draft authored from Danny's 2026-06-30 conversation requesting a Previous / Next delivery indicator on each item in the Order Items by Category section, a section-level All / Previous / Next filter defaulting to Next, and an auto-flip behaviour that reclassifies items without a data sync. The spec adds 12 FRs, 4 NFRs, 13 acceptance scenarios, and reuses existing entities (`OrderBlob.deliveryDate`, `DeliveryWindow.date`, the dashboard's existing `today` value) without modifying any loader / pipeline / cron.
- Status after change: `Draft`.
- Rationale: Danny flagged the time-dependent auto-flip as the harder design question. The honest answer — that the dashboard already loads every order blob, so the classification is a pure render-time derivation over the existing `validOrders` array, no sync needed — is the architectural choice. The pending-next placeholder (FR-006) handles the gap case honestly rather than fabricating items.
- Implementation impact: None (this is a Draft; no implementation work has started). When implemented, this spec will touch `components/dashboard-client.tsx`, `components/delivery-badge.tsx` (new), `lib/dashboard-data.ts` (additive `validOrders` field), `lib/item-utils.ts` (new pure helper), `components/dashboard-debug-chips.tsx`, and `lib/fixtures/scripts/generate-fixture.mjs` (optional, only if a two-delivery fixture is not already available). No Python pipeline, no cron, no blob namespace changes.
- Evidence: Danny's request in this conversation; spec 008 (the parent spec) for the existing pipeline semantics; spec 018 for the cancelled/superseded/refunded status handling; spec 022 for the debug-mode-only constraint on the time-machine smoke test.
