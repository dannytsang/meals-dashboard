### 2026-06-18 — Proposed (created)

- Change: Created `028-dashboard-blob-head-read-savings/` as a Proposed feature. Spec formalises a Vercel Blob SDK method swap inside `lib/blob-storage.ts`: replace `list({prefix: path})` with `head(path)` in `VercelBlobStorageClient.readPointer` and `readManifest` to downgrade those two reads from Vercel Blob Advanced Operations to Simple Operations. 6 functional requirements (FR-001 through FR-006), 3 non-functional requirements (NFR-001 through NFR-003), 3 user stories (US1, US2, US3 — P1×2 + P2×1), 1 key entity (one existing module: `lib/blob-storage.ts`, plus test additions), 2 open questions (extending head() to readJsonBlob, 404 vs empty-array semantic equivalence), 3 risks (SDK API surface change, Vercel pricing reclassification, warm module cache after deploy). `readJsonBlob` is intentionally NOT changed (FR-006) — it accepts arbitrary pathnames from runtime data where `list({prefix})` is the right tool. The `InMemoryBlobStorageClient` test fixture is also unchanged (it never calls the Vercel SDK).
- Status after change: Proposed
- Rationale: On 2026-06-18 Danny asked whether the Vercel Blob product metadata writes are the dominant cost driver. They aren't — the real cost reduction opportunity is in the **read** path. Each meals-check sync begins with two `list()` calls (pointer + manifest). Per Vercel's pricing page (https://vercel.com/docs/vercel-blob/usage-and-pricing), `head()` is a Simple Operation (10K included/month on Hobby, $0.40 per 1M over-allowance) while `list()` is an Advanced Operation (2K included/month on Hobby, $5.00 per 1M over-allowance) — `head()` is 12.5× cheaper at over-allowance and 5× more included quota. The `readPointer` and `readManifest` methods both know the exact blob pathname they want to read (`POINTER_PATH` is a constant for `readPointer`; `readManifest` receives the path from the pointer JSON), so `list({prefix})` was the wrong tool all along. `head()` returns the same `{url, pathname}` metadata without a list scan, and the existing `fetch()` call reads the body. Same network calls as today, but the lookup is downgraded from Advanced to Simple. The spec ships as Proposed because the production-evidence gate (Promotion Criteria items 1-6) cannot be crossed in this session — it requires observing Vercel function logs on the production deploy showing `list()` calls dropping from 2 to 0 in the route handler invocation path, and that observation happens after Danny triggers a sync run on the deployed build.
- Implementation impact: Two files modified, no files created in the meals-dashboard repo. `lib/blob-storage.ts:62-66` (`readPointer`) and `lib/blob-storage.ts:68-77` (`readManifest`) swap `list({prefix: path})` for `head(path)`. The `head` symbol is added to the existing imports at line 2. `lib/blob-storage.test.ts` gains 5 new vitest cases (one per scenario in `scenarios.yaml` that requires vitest). No new dependencies, no new env vars, no new Vercel Functions, no new Route Handlers, no schema changes, no data migrations. The `BlobStorageClient` interface is unchanged (NFR-001 + NFR-003). The `InMemoryBlobStorageClient` test fixture is unchanged. The dashboard read path (`lib/dashboard-data.ts`, `lib/dashboard-ui-utils.ts`) is unchanged. The Python sync pipeline (`scripts/sync-dashboard-data.py`) is unchanged. The legacy `/api/dashboard-data` endpoint is unchanged. Production deploy is via `git push origin main` (Vercel auto-deploy hook).
- Evidence: Vercel Blob pricing page (https://vercel.com/docs/vercel-blob/usage-and-pricing) is the authoritative source for the Advanced vs Simple operation classification. `@vercel/blob@2.4.0` (installed at `/home/hermes/workspace/meals-dashboard/node_modules/@vercel/blob`) exposes the `head()` SDK method at `dist/index.d.ts:121` with signature `declare function head(urlOrPathname: string, options?: BlobCommandOptions): Promise<HeadBlobResult>;`. The `HeadBlobResult` shape (`{size, uploadedAt, pathname, contentType, contentDisposition, url, downloadUrl, cacheControl, etag}`) at `dist/index.d.ts:76-113` matches the existing `readJsonBlob` `match` usage at `lib/blob-storage.ts:81`. The 404→null return path is verified at `dist/index.js:172-173` (`if (response.status === 404) { return null; }`). The actual meals-check sync run on 2026-06-18 (logged in `/home/hermes/.hermes/cron/output/tesco-meal-check-2026-06-18.txt`) reported `Written: 2 | Skipped: 16 | Total ops: 4` — but this `totalOps` count from `syncDashboardLayout` does not include the two `list()` reads at the start of the sync, nor the legacy `put()` to `dashboard-data.json`. The full Vercel Blob operation cost is 9 advanced ops per sync (2 list + 3 data put + 2 manifest/pointer put + 1 del + 1 legacy put). After spec 028 lands, this drops to 7 advanced ops per sync (0 list + 3 data put + 2 manifest/pointer put + 1 del + 1 legacy put) — a 22% reduction. Danny's hunch about product writes being the cost driver was understandable (the Python sync assembles 11 product blobs per sync) but the dedup + content-hash design means only 2 actually write per sync — the savings opportunity is in the read path instead. The spec location decision follows the boundary doc at `references/meals-dashboard-repo-boundary-and-spec-location.md`: specs live in `data-science/meals-check/.specify/specs/` (versioned alongside the meals-check skill), not in `/home/hermes/plans/` (which is not a git repo on this host).
