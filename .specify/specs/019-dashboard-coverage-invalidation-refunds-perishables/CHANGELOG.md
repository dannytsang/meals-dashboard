### 2026-06-15 — Phase 6 shipped: manual override persistence

- Change: Implemented Phase 6 of 019 in `tesco_meal_check.py`. The new `apply_manual_override(*, meal_date, meal_name, item_name, quantity, reason, status, overrides_path, audit_log_path)` API persists override entries to a JSON file at `~/.hermes/scripts/data/manual_overrides.json`. The triple `(meal_date, meal_name, item_name)` is the unique key — re-applying the same triple updates the existing entry rather than appending a duplicate. The new `load_dashboard_overrides()` reader returns a list of active (non-cleared) entries. `write_dashboard_cache` now calls `load_dashboard_overrides()` and merges via the existing `apply_manual_overrides()` function with a thin shape adapter that maps the JSON shape onto the legacy YAML shape the matcher expects. A new `pipeline.dashboard_overrides_file` config in `tesco_config.yaml` controls the path (default `data/manual_overrides.json`). Every override write appends a `manual_override_applied` entry to the audit log with `meal_date`, `meal_name`, `item_name`, `quantity`, `status`, `reason`, and `operation` (created vs updated).
- Status after change: Proposed
- Rationale: Phase 6 is the persistence target for the dashboard's "I have this" button (T061, T062) and the four-item-state UI (T060). The new JSON file is a separate store from the existing `meal_manual_overrides.yaml` (the human-edited planning aid) because they serve different purposes: YAML is Danny's planning input, JSON is the dashboard's machine-written output. The triple key in the JSON file makes "I have this" idempotent — clicking the button twice doesn't create duplicate entries. Per SC-04 Acceptance 5, the override's own `status` field is the authoritative answer; the override does not silently upgrade a partial meal to covered.
- Implementation impact: `tesco_meal_check.py` +200 lines: `apply_manual_override()` (75 lines), `load_dashboard_overrides()` (30 lines), `_dashboard_overrides_to_legacy_shape()` (15 lines), `DASHBOARD_OVERRIDES_FILE` config (5 lines), `write_dashboard_cache` integration (8 lines). `test_tesco_manual_override_persistence.py` is a new file (7 cases, ~265 lines). No change to the matcher allocation logic; no change to the dashboard code (the override file is read by the Python pipeline; the dashboard side will need an API route in Phase 7 to call `apply_manual_override`).
- Evidence: RED — `python3 -m unittest test_tesco_manual_override_persistence` failed with `AttributeError: module 'tesco_meal_check' has no attribute 'apply_manual_override'` and `'load_dashboard_overrides'`. ### 2026-06-14 — Add coverage invalidation on order cancellation/movement (carried over from parent)

- Change: Original 016 spec added FR-005 for coverage invalidation on order status changes. Coverage blobs contain `sourceOrderBlobPath` and `stale` / `staleReason` fields. When an order's status changes, the pipeline marks affected coverage blobs `stale: true` and recalculates. Carried over verbatim and forms FR-001 and FR-002 of this feature.
- Status after change: Proposed (this slice)
- Rationale: Stale coverage without invalidation would silently misrepresent which meals are actually covered.
- Implementation impact: `tesco_meal_check.py`: when order status changes, find all coverage blobs whose `date` falls within the order's coverage window, write stale versions, recalculate, write new versions. `coverage/{date}.json` schema gains `sourceOrderBlobPath`, `stale`, `staleReason` fields. Dashboard must render "⚠️ stale coverage" indicator.
- Evidence: Scenario 3.2 analysis confirmed stale coverage problem.

### 2026-06-14 — Extend coverage invalidation trigger to cover amendments (carried over from parent)

- Change: Original 016 spec extended FR-005 to trigger on any order blob content change (amendment + or - items), not just status changes. Trigger types: `order_updated` (amendment), `order_cancelled`, `order_superseded`, `order_refunded`. Carried over verbatim into FR-001 of this feature.
- Status after change: Proposed (this slice)
- Rationale: An amendment email with added items could match previously unmatched meals. Without recalculation, the dashboard would show `missing` for a meal that should now be `covered`.
- Implementation impact: `tesco_meal_check.py`: on every order blob write, compare new item list with previous item list. If items differ, trigger coverage invalidation.
- Evidence: Scenario 3.4 analysis.

### 2026-06-14 — Shelf-life-aware matching (carried over from parent)

- Evidence: Scenario 3.8.

### 2026-06-14 — Manual override (carried over from parent)

- Change: Original 016 spec added FR-009 for manual override. Danny marks a missing item as "I have this"; coverage blob updated with `override_found: true`, `override_source: "manual"`, `override_timestamp`. Audit log entry. Override persisted in local state (`manual_overrides.json`). Meal status not auto-upgraded. Dashboard meal detail card differentiates four item states. Manual override acknowledges pantry/fridge coverage without requiring the algorithm to track pantry state across weeks.
