### 2026-06-17 — Final (Rev 3: env-var kill switch removed; cookie is the only gate)

- Change: Replaced the Rev 2 two-level switch (env-var `MEALS_DEBUG_MODE` + per-user signed cookie) with a single per-user signed cookie (`meals_debug_mode`, HMAC-SHA-256 keyed on `NEXTAUTH_SECRET`) as the only gate. The env-var added ops friction with no security benefit — the cookie is HMAC-signed (tamper-evident), the OIDC gate is inherited, and the debug surface only exposes data the dashboard already shows. There is no longer a `MEALS_DEBUG_MODE` env-var read anywhere in the dashboard, no `isDebugModeEnabled()` env-only helper, and no `envEnabled` prop on the toggle. The toggle is always interactive when rendered. If a global disable is ever needed, the answer is "delete the toggle component" or "revert the merge", not "set an env-var and re-deploy". Spec body, plan, tasks, scenarios, traceability, and references doc updated to Rev 3 throughout (env-var references purged from US1, FR-001/002/003/011/013/014, Open Question 7 re-resolved, Promotion Criteria block rewritten for cookie-only evidence). Status flipped from `Proposed` to `Final, readiness: already_satisfied` after the *off* state was verified live on the production deployment.
- Status after change: Final (Rev 3)
- Rationale: Danny asked on 2026-06-17 (after the merge to `preview` in commit `089c915` of spec 022 Rev 2) "change the debug mode to a UI control, not env" — i.e. drop the env-var and keep only the cookie. Rev 2 had two levels: the env-var (deployment kill switch) and the cookie (per-user switch). Rev 3 collapses to one: the cookie. The OIDC gate, the HMAC signature, the `__NEXT_DATA__` discipline, and the dynamic-import boundary together make the env-var redundant: the cookie's tamper-evidence already provides the security boundary the env-var was adding, and the OIDC middleware runs first so unauthenticated users never reach the debug code path.
- Implementation impact: `lib/debug-mode.ts` shrinks — `effectiveDebugMode(cookieRaw)` is now a thin wrapper over `verifyDebugCookie`, with no `process.env` reads. `app/api/debug/toggle/route.ts` always accepts the cookie flip (the 404-when-env-off branch is removed). `app/api/debug/items-by-category/route.ts` and `app/debug/page.tsx` are cookie-only. `app/debug/page.tsx` no longer reads `MEALS_DEBUG_MODE`; the footer row is replaced with the Vercel deployment ID, passed as a prop from the server component. `components/debug-toggle.tsx` and `components/dashboard-client.tsx` drop the `envEnabled` prop — the toggle is always interactive. All test files updated: `lib/debug-mode.test.ts` now covers the cookie-only contract (7 tests), `app/api/debug/items-by-category/route.test.ts` covers unset/signed/tampered/unsigned paths (7 tests), `app/api/debug/toggle/route.test.ts` covers the flip paths (11 tests). The env-off 404 tests are removed. Spec body, plan.md, tasks.md, scenarios.yaml, traceability.yaml, and `references/dashboard-debug-mode.md` are all rewritten in this commit.

### 2026-06-17 — Proposed (Rev 2: UI control replaces URL flag)

- Change: Replaced the `?debug=inject` URL flag with an in-header UI toggle (Bug icon) that flips a per-user signed cookie (`meals_debug_mode`, HMAC-SHA-256 keyed on `NEXTAUTH_SECRET`). The two-level switch (env-var + per-user cookie) gives the operator a per-deployment kill switch AND a per-user switch without a redeploy. The env-var dominates: a signed "1" cookie alone cannot turn debug on when the env is off. The cookie is tamper-evident: setting `meals_debug_mode=1` in devtools without the server's HMAC has no effect. The `?debug=inject` URL mechanism was removed (it was non-stateful and easy to forget). The inline debug chips on the main dashboard are now controlled by the cookie alone (no URL flag). The `lib/debug-cookie.ts` helper is the single source of truth for sign/verify. The `lib/debug-mode.ts` helper now exports `isDebugModeEnabled()` (env-only, used by the toggle route to decide whether to accept the cookie flip) and `effectiveDebugMode(cookieRaw)` (env+cookie, used by `/debug` and `/api/debug/*` to decide whether to serve the surface). All server-side code that decides whether to render debug UI goes through one of these helpers. Spec body updated to Rev 2: Background, US1 (renamed "Two-Level Server-Side Feature Switch"), US2 (new — "In-Header UI Toggle"), US4 (renamed "Inline Debug Chips on the Main Dashboard"), US5 (renamed "Documented Enablement"), FR-001 (two-level), FR-002 (env dominates cookie), FR-003 (env+cookie), FR-007 (footer shows env + cookie + deployment), FR-008 (new `app/api/debug/toggle/route.ts` + `components/debug-toggle.tsx`), FR-009 (cookie replaces URL flag), FR-011 (`effectiveDebugMode`), FR-012 (new — cookie helper contract), FR-013 (build gates), FR-014 (test of `effectiveDebugMode`), FR-015 (new — cookie test), FR-017 (cookie is the only persistence), FR-019 (expected_artifacts updated), NFR-006 (new — tamper-evident cookie), Open Question 5 (re-resolved: cookie is the per-user switch, replacing the URL flag), Open Question 7 (new — toggle visibility policy: hidden when env off), Open Question 8 (new — `Secure` in production only). Promotion Criteria block updated: production bundle must also be grep-clean for `meals_debug_mode`. CHANGELOG, plan, tasks, scenarios, traceability, index, references/dashboard-debug-mode.md, and skill.spec.yaml `expected_artifacts:` updated to match. New files: `app/api/debug/toggle/route.ts`, `app/api/debug/toggle/route.test.ts`, `components/debug-toggle.tsx`, `lib/debug-cookie.ts`, `lib/debug-cookie.test.ts`. Modified: `app/debug/page.tsx`, `app/api/debug/items-by-category/route.ts` + test, `app/page.tsx`, `components/dashboard-client.tsx`, `components/debug-shell.tsx`, `components/dashboard-debug-chips.tsx`, `components/items-by-category-debug-panel.tsx` (doc-only), `lib/debug-mode.ts` + test, `references/dashboard-debug-mode.md`.
- Status after change: Proposed (Rev 2)
- Rationale: Danny asked on 2026-06-17 "change the debug mode to a UI control, not env". The Rev 1 design had three issues that the UI control resolves: (1) the `?debug=inject` URL flag was easy to forget and didn't persist across sessions; (2) the env-var alone required a redeploy to flip for a single user; (3) the operator had to reach for the URL bar every time they wanted to inspect a surface. Rev 2 keeps the env-var as the deployment kill switch (the security boundary) and adds a per-user signed cookie flipped by an in-header toggle (the operator ergonomics). The cookie is tamper-evident (HMAC-SHA-256), HttpOnly, SameSite=Lax, 30-day Max-Age, Secure in production only. The env still dominates: a signed "1" cookie alone cannot turn debug on when the env is off. All security guarantees from Rev 1 are preserved; the new attack surface (a tampered cookie) is closed by the HMAC.
- Implementation impact: New: `app/api/debug/toggle/route.ts`, `app/api/debug/toggle/route.test.ts`, `components/debug-toggle.tsx`, `lib/debug-cookie.ts`, `lib/debug-cookie.test.ts`. Modified: `app/debug/page.tsx`, `app/api/debug/items-by-category/route.ts` + test (now gated on `effectiveDebugMode(cookieRaw)` instead of `isDebugModeEnabled()`), `app/page.tsx` (passes `debugOn` and `envEnabled` instead of `debugInject`), `components/dashboard-client.tsx` (renders the toggle, drops `debugInject` prop, replaces with `debugOn` + `envEnabled`), `components/debug-shell.tsx` (footer shows cookie value), `components/dashboard-debug-chips.tsx` (doc-only), `components/items-by-category-debug-panel.tsx` (doc-only), `lib/debug-mode.ts` + test (adds `effectiveDebugMode`), `references/dashboard-debug-mode.md` (rewritten for the two-level switch), `skill.spec.yaml` `expected_artifacts:` (+4 new files). The `?debug=inject` URL mechanism is fully removed; bookmarks and curl scripts that used it will silently no-op (the dashboard renders as production). All test, build, and bundle-grep gates from Rev 1 still apply; the new tamper-evident cookie is verified by `lib/debug-cookie.test.ts` (25 tests) and the new `app/api/debug/toggle/route.test.ts` (11 tests).
